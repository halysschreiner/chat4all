# RF02 - Autenticação de Usuários: Análise de Implementação

---

## 1. Resumo do Requisito

### Transcrição do RF02

> **RF02 - Autenticação de Usuários**
> - Implementar autenticação via JWT (JSON Web Token).
> - Endpoint `POST /v1/auth/login` para autenticação de usuários.
> - Usuários devem ser identificados por um nome único (username).
> - O servidor deve registrar quem está conectado e garantir a entrega de mensagens apenas aos destinatários corretos.

### Importância no Contexto do Sistema

RF02 é o **requisito de segurança primário** do Chat4All. Em sistemas de mensageria distribuídos, a autenticação serve três propósitos críticos:

1. **Controle de Acesso**: Apenas usuários autenticados podem enviar/receber mensagens
2. **Isolamento de Sessão**: JWT contém `user_id` que identifica o remetente em cada operação
3. **Auditoria**: O campo `sub` do JWT permite rastrear ações por usuário

**Conceito teórico**: JWT segue a **RFC 7519** e implementa o padrão **Bearer Token** (RFC 6750). É um token **stateless** — o servidor não precisa armazenar sessão, permitindo escalabilidade horizontal sem session affinity.

## 2. Solução Arquitetural

### 2.1 Arquitetura de Autenticação

```
┌─────────────────┐                    ┌───────────────────┐
│   Frontend      │  POST /v1/auth/    │   API Gateway     │
│   (Angular)     │ ───────────────────▶│   (PHP)           │
│                 │       login         │   :8000           │
└─────────────────┘                    └─────────┬─────────┘
                                                 │ gRPC
                                                 ▼
                                       ┌───────────────────┐
                                       │   AuthService     │
                                       │   (gRPC Server)   │
                                       │   :50051          │
                                       └─────────┬─────────┘
                                                 │
                            ┌────────────────────┼────────────────────┐
                            │                    │                    │
                            ▼                    ▼                    ▼
                   ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
                   │   PostgreSQL   │   │     Redis      │   │  JWT Library   │
                   │   (Usuários)   │   │   (Sessions)   │   │  (firebase/jwt)│
                   └────────────────┘   └────────────────┘   └────────────────┘
```

### 2.2 Fluxo de Autenticação

1. **Login Request**: Cliente envia `email/phone` + `password`
2. **Validação**: `AuthService` consulta PostgreSQL, verifica hash bcrypt
3. **Token Generation**: Se válido, gera JWT com `HS256`
4. **Token Storage (opcional)**: Redis pode cachear sessão para blacklist/revogação
5. **Response**: Retorna `{ token, user }`

### 2.3 Trade-offs da Arquitetura

| Aspecto | Escolha | Trade-off |
|---------|---------|-----------|
| **Stateless JWT** | ✅ | (+) Escalabilidade horizontal sem compartilhar estado. (-) Revogação imediata impossível sem blacklist |
| **HS256 (Simétrico)** | ✅ | (+) Performance ~10x melhor que RS256. (-) Chave compartilhada entre serviços |
| **bcrypt** | ✅ | (+) Resistente a brute-force (cost factor). (-) CPU-intensive (~250ms/hash) |

### 2.4 Alternativas Descartadas

#### Alternativa 1: OAuth 2.0 / OpenID Connect

**Por que descartada**: Complexidade desnecessária para sistema single-tenant acadêmico. OAuth requer Authorization Server separado (Keycloak/Auth0).

**Trade-off sacrificado**: Federação de identidade, Single Sign-On.

#### Alternativa 2: Session-based Auth (Cookie + Redis)

**Por que descartada**: Viola princípio stateless exigido para escalabilidade horizontal. WebSocket em porta diferente não compartilha cookies facilmente.

**Trade-off sacrificado**: Revogação instantânea de sessão.

## 3. Stack Tecnológica

| Tecnologia | Papel | Versão |
|------------|-------|--------|
| **firebase/php-jwt** | Geração e validação de tokens | ^6.0 |
| **password_hash (bcrypt)** | Hash de senhas | PHP 8.3 built-in |
| **PostgreSQL** | Armazenamento de usuários | 16 |
| **Redis** | Cache de sessões (opcional) | 7 |

### 3.1 firebase/php-jwt

**Por que escolhida**:
- Biblioteca oficial do Firebase, amplamente auditada
- Suporte a múltiplos algoritmos (HS256, RS256, ES256)
- API simples: `JWT::encode()`, `JWT::decode()`

**Trade-offs**:
| Ganho | Limitação |
|-------|-----------|
| Código-fonte auditável | Não valida claims customizados automaticamente |
| Performance otimizada | Sem suporte nativo a refresh tokens |

**Alternativas consideradas**:
- **lcobucci/jwt**: Mais type-safe, mas verboso
- **namshi/jose**: Menos mantido ativamente

### 3.2 bcrypt (PASSWORD_BCRYPT)

**Por que escolhida**:
- **Adaptive**: Cost factor ajustável (default: 10 → ~100ms)
- **Salted**: Salt único por hash, evita rainbow tables
- **PHP nativo**: `password_hash()` / `password_verify()`

**Trade-offs**:
| Ganho | Limitação |
|-------|-----------|
| Resistente a GPU cracking | CPU-intensive em alta concorrência |
| Salt automático | ~250ms por verificação (cost=12) |

**Conceito teórico**: bcrypt implementa **key derivation function (KDF)** baseada em Blowfish. O cost factor de 10-12 balanceia segurança vs performance para ~100-300ms.

### 4.2 Componentes Críticos

#### 4.2.1 AuthService - Login (`services/api-service/src/Grpc/AuthService.php`)

**Linhas 74-121**:
```php
public function Login(LoginRequest $request): LoginResponse
{
    $response = new LoginResponse();
    
    try {
        $email = $request->getEmail();
        $phone = $request->getPhone();
        $password = $request->getPassword();
        
        $identifier = $email ?: $phone;
        if (!$identifier) {
            throw new \Exception("Email or Phone is required");
        }
        
        $user = $this->database->getUserByEmailOrPhone($identifier);
        
        // SEGURANÇA: password_verify é timing-safe (constant-time comparison)
        // Evita timing attacks que poderiam revelar se email existe
        if (!$user || !password_verify($password, $user['password_hash'])) {
            throw new \Exception("Invalid credentials");
        }
        
        // Generate JWT
        $payload = [
            'iss' => 'chat4all-api',      // Issuer
            'sub' => $user['user_id'],     // Subject (user identifier)
            'iat' => time(),               // Issued At
            'exp' => time() + 3600,        // Expiration (1 hour)
            'username' => $user['username'],
            'email' => $user['email']
        ];
        
        $token = JWT::encode($payload, $this->jwtSecret, 'HS256');
        // ...
    }
}
```

**Conceitos implementados**:
1. **Timing-safe comparison**: `password_verify()` usa comparação constant-time
2. **Claims padrão JWT (RFC 7519)**: `iss`, `sub`, `iat`, `exp`
3. **Claims customizados**: `username`, `email` para conveniência

#### 4.2.4 Validação de Token (`services/api-service/src/Grpc/AuthService.php`)

**Linhas 123-145**:
```php
public function ValidateToken(\Auth\ValidateTokenRequest $request): \Auth\ValidateTokenResponse
{
    $response = new \Auth\ValidateTokenResponse();
    
    try {
        $token = $request->getToken();
        
        // JWT::decode valida:
        // 1. Assinatura (HS256)
        // 2. Expiração (exp claim)
        // 3. Estrutura do token
        $decoded = JWT::decode($token, new \Firebase\JWT\Key($this->jwtSecret, 'HS256'));
        
        $response->setValid(true);
        $response->setUserId($decoded->sub);
        $response->setMessage("Token is valid");
        
    } catch (\Exception $e) {
        $this->logger->warning("Token validation failed: " . $e->getMessage());
        $response->setValid(false);
        $response->setMessage($e->getMessage());
    }
    
    return $response;
}
```

#### 4.2.5 Schema do Banco (`scripts/init-db.sql`)

**Linhas 11-25**:
```sql
CREATE TABLE IF NOT EXISTS users (
    user_id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    username VARCHAR(255) UNIQUE NOT NULL,
    email VARCHAR(255) UNIQUE,
    phone VARCHAR(20) UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    status VARCHAR(20) DEFAULT 'active' CHECK (status IN ('active', 'suspended', 'deleted')),
    -- Pelo menos email OU phone deve existir
    CONSTRAINT email_or_phone_check CHECK (email IS NOT NULL OR phone IS NOT NULL)
);

CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_phone ON users(phone);
CREATE INDEX idx_users_username ON users(username);
```

**Decisões de modelagem**:
- `UUID v4`: Evita exposição de contagem de usuários (vs auto-increment)
- `UNIQUE` em username/email/phone: Constraint no banco como última defesa
- Índices separados: Otimiza lookups por email OU phone

## 5. Análise Crítica

### 5.1 Conformidade com o Requisito

| Sub-requisito | Status | Evidência |
|---------------|--------|-----------|
| JWT authentication | ✅ **Atendido** | `firebase/php-jwt` em `AuthService.php` |
| Endpoint POST /v1/auth/login | ✅ **Atendido** | `api-gateway/public/index.php:91` |
| Username único | ✅ **Atendido** | `UNIQUE` constraint em `init-db.sql:13` |
| Registro de conectados | ⚠️ **Parcial** | WebSocket mantém mapeamento, mas não há lista global |
| Entrega correta de mensagens | ✅ **Atendido** | JWT `sub` usado para identificar remetente em `MessageService` |

### 5.2 Limitações Identificadas

#### Limitação 1: Ausência de Refresh Token

**Problema**: Token expira em 1 hora sem mecanismo de renovação silenciosa.

**Impacto**: Usuário precisa fazer login novamente após expiração.

**Solução proposta**:
```php
// Adicionar refresh_token com TTL maior (7 dias)
$refreshPayload = [
    'sub' => $user['user_id'],
    'type' => 'refresh',
    'exp' => time() + (7 * 24 * 3600),
];
$refreshToken = JWT::encode($refreshPayload, $this->jwtRefreshSecret, 'HS256');
```

#### Limitação 2: Sem Blacklist de Tokens

**Problema**: Não é possível revogar tokens antes da expiração (logout imediato).

**Impacto**: Token roubado permanece válido por até 1 hora.

**Solução proposta**: Usar Redis para blacklist:
```php
// No logout
$redis->setex('blacklist:' . $tokenHash, 3600, '1');

// Na validação
if ($redis->exists('blacklist:' . $tokenHash)) {
    throw new \Exception('Token revoked');
}
```

#### Limitação 3: Mesma Secret Key em Todos os Serviços

**Problema**: Comprometimento de um serviço expõe a chave para todos.

**Impacto**: Atacante pode forjar tokens válidos para qualquer usuário.

**Solução proposta**: Migrar para **RS256** (assimétrico):
- Chave privada apenas no AuthService (assinatura)
- Chave pública distribuída para validação

### 5.3 Pontos Fortes

1. **Stateless**: JWT permite escalar API horizontalmente sem session store
2. **Constant-time verification**: `password_verify` previne timing attacks
3. **UUID**: Não expõe contagem de usuários
4. **Separação Gateway/Service**: Limita superfície de ataque
