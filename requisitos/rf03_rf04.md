# RF03 e RF04 - Mensagens Privadas e em Grupo: Análise de Implementação

---

## 1. Resumo dos Requisitos

### Transcrição do RF03 - Mensagens Privadas

> - Permitir que um usuário envie uma mensagem de texto a outro usuário conectado.
> - O receptor deve receber em tempo real a mensagem, desde que esteja conectado.
> - Endpoint `POST /v1/messages` para envio de mensagens de texto.
> - Endpoint `GET /v1/conversations/{id}/messages` para listar mensagens de uma conversa.

### Transcrição do RF04 - Mensagens em Grupo

> - O sistema deve suportar a criação de grupos de usuários.
> - Mensagens enviadas a um grupo devem ser distribuídas automaticamente a todos os membros.
> - Endpoint `GET /v1/conversations` para listar conversas do usuário.

### Importância no Contexto do Sistema

RF03 e RF04 são os **requisitos core** do sistema — a razão de existência do Chat4All. Eles implementam o padrão **Store-and-Forward** de mensageria:

1. **Store**: Mensagem persistida no PostgreSQL antes de qualquer processamento
2. **Forward**: Kafka distribui para workers que notificam destinatários via WebSocket

**Conceitos de Sistemas Distribuídos envolvidos**:
- **Eventual Consistency**: Mensagem salva → publicada no Kafka → consumida → status atualizado
- **Particionamento**: Mensagens agrupadas por `conversation_id` para ordenação garantida
- **Fan-out**: Em grupos, uma mensagem gera N notificações (1 por membro)

### 2.2 Modelo de Dados

```sql
-- Conversa (privada ou grupo)
conversations (
    conversation_id UUID PK,
    type VARCHAR CHECK ('private', 'group'),
    name VARCHAR,                    -- NULL para privadas
    created_by UUID FK users,
    last_message_snippet TEXT        -- Desnormalização para performance
)

-- Membros da conversa
conversation_members (
    conversation_id UUID FK,
    user_id UUID FK,
    role VARCHAR CHECK ('owner', 'admin', 'member'),
    last_read_at TIMESTAMP           -- Para contagem de não-lidas
)

-- Mensagens
messages (
    message_id UUID PK,
    conversation_id UUID FK,
    from_user_id UUID FK,
    content TEXT,
    message_type VARCHAR,            -- 'text', 'file', 'image'
    status VARCHAR,                  -- 'SENT', 'DELIVERED', 'READ'
    sequence_number BIGSERIAL        -- Ordenação determinística
)
```

### 2.3 Diferenças entre Privada e Grupo

| Aspecto | Conversa Privada | Grupo |
|---------|------------------|-------|
| **Membros** | Exatamente 2 | 2+ |
| **Nome** | NULL (exibe nome do outro) | Obrigatório |
| **Roles** | owner + member | owner, admin, member |
| **Fan-out** | 1 notificação | N-1 notificações |
| **Criação** | Automática ao enviar 1ª msg | Explícita |

### 2.4 Alternativas Arquiteturais Descartadas

#### Alternativa 1: CQRS (Command Query Responsibility Segregation)

**Descrição**: Separar modelo de escrita (commands) e leitura (queries) com event sourcing.

**Por que descartada**: 
- Overhead de sincronização entre modelos
- Complexidade desnecessária para escala acadêmica
- Eventual consistency mais difícil de raciocinar

**Trade-off sacrificado**: Escalabilidade de leitura independente.

#### Alternativa 2: Polling HTTP

**Descrição**: Cliente faz `GET /messages` periodicamente.

**Por que descartada**:
- Viola requisito "tempo real"
- Latência proporcional ao intervalo de polling
- Desperdício de banda (99% das requisições sem novidades)

**Trade-off sacrificado**: Simplicidade de implementação.

## 3. Stack Tecnológica

| Tecnologia | Papel | Justificativa |
|------------|-------|---------------|
| **Apache Kafka** | Event streaming | Particionamento por `conversation_id` garante ordem |
| **PostgreSQL** | Persistência | ACID para operações transacionais |
| **gRPC** | RPC interno | Serialização binária eficiente |
| **WebSocket (Ratchet)** | Notificações | Full-duplex para push instantâneo |
| **UUID v4** | IDs | Evita colisões em ambiente distribuído |

### 3.1 Kafka para Mensageria

**Por que Kafka e não filas tradicionais?**

| Kafka | RabbitMQ |
|-------|----------|
| **Log imutável**: Replay possível | Mensagem removida após consumo |
| **Partições**: Paralelismo garantido | Múltiplas filas manuais |
| **Consumer Groups**: Rebalanceamento automático | Configuração manual |
| **Retenção**: Mensagens persistidas por dias | Apenas em memória/disco |

**Particionamento por conversation_id**:
```php
$this->kafkaProducer->publish(
    $payload,
    $conversationId // Key para particionamento
);
```

Isso garante que mensagens da mesma conversa vão para a **mesma partição**, mantendo **ordenação FIFO**.

### 4.2 Componentes Críticos

#### 4.2.1 Envio de Mensagem (`MessageService.php`)

**Linhas 37-91**:
```php
public function SendMessage(SendMessageRequest $request): SendMessageResponse
{
    $response = new SendMessageResponse();
    
    try {
        $conversationId = $request->getConversationId();
        $fromUserId = $request->getFromUserId();
        $content = $request->getContent();
        $messageType = $request->getMessageType() ?: 'text';
        $fileId = $request->getFileId() ?: null;
        
        // UUID v4: Globalmente único sem coordenação central
        $messageId = Uuid::uuid4()->toString();
        $timestamp = date('Y-m-d H:i:s');
        
        $payload = [
            'message_id' => $messageId,
            'conversation_id' => $conversationId,
            'from_user_id' => $fromUserId,
            'content' => $content,
            'message_type' => $messageType,
            'file_id' => $fileId,
            'status' => 'SENT',  // Status inicial
            'created_at' => $timestamp
        ];
        
        // PERSISTÊNCIA PRIMEIRO (Outbox Pattern simplificado)
        // Se Kafka falhar, mensagem ainda está no banco
        $this->database->insertMessage($payload);
        
        // Publicar no Kafka para processamento assíncrono
        // Key = conversation_id para garantir ordem
        $this->kafkaProducer->publish(
            $payload,
            $conversationId
        );
        
        $response->setSuccess(true);
        $response->setMessage("Message sent to queue");
        // ...
    }
}
```

**Padrões aplicados**:
1. **Write-Ahead**: Persiste no banco ANTES de publicar no Kafka
2. **Partition Key**: `conversation_id` garante ordem dentro da conversa
3. **Idempotência**: UUID como PK permite retry sem duplicação

#### 4.2.2 Criação de Conversa Privada (`ConversationService.php`)

**Linhas 27-78**:
```php
public function CreatePrivateConversation(CreatePrivateConversationRequest $request): CreateConversationResponse
{
    $response = new CreateConversationResponse();
    
    try {
        $userId = $request->getUserId();
        $otherUserId = $request->getOtherUserId();
        
        // Validações de negócio
        if ($userId === $otherUserId) {
            throw new \Exception("Cannot create conversation with yourself");
        }
        
        // Buscar usuário por UUID, email ou phone
        if (preg_match('/^[0-9a-fA-F-]{36}$/', $otherUserId)) {
            $otherUser = $this->database->getUserById($otherUserId);
        }
        if (!$otherUser) {
            $otherUser = $this->database->getUserByEmailOrPhone($otherUserId);
        }
        
        // IDEMPOTÊNCIA: Se conversa já existe, retorna a existente
        $existingId = $this->database->checkPrivateConversationExists($userId, $otherUserId);
        
        if ($existingId) {
            $conversationData = $this->database->getConversationById($existingId);
            $response->setMessage("Conversation already exists");
        } else {
            // Criar nova conversa tipo 'private'
            $conversationId = $this->database->createConversation('private', null, $userId);
            $this->database->addConversationMember($conversationId, $userId, 'owner');
            $this->database->addConversationMember($conversationId, $otherUserId, 'member');
            
            $conversationData = $this->database->getConversationById($conversationId);
            $response->setMessage("Conversation created successfully");
        }
        
        $response->setSuccess(true);
        $response->setConversation($this->mapConversation($conversationData));
    }
    // ...
}
```

**Decisões importantes**:
1. **Idempotência**: Não cria duplicata se conversa já existe
2. **Flexibilidade de lookup**: Aceita UUID, email ou phone
3. **Roles**: Criador é `owner`, outro é `member`

#### 4.2.3 Criação de Grupo (`ConversationService.php`)

**Linhas 80-127**:
```php
public function CreateGroup(CreateGroupRequest $request): CreateConversationResponse
{
    $response = new CreateConversationResponse();
    
    try {
        $userId = $request->getUserId();
        $groupName = $request->getGroupName();
        $memberIds = $request->getMemberUserIds();
        
        if (!$groupName) {
            throw new \Exception("Group name is required");
        }
        
        // Criar conversa tipo 'group'
        $conversationId = $this->database->createConversation('group', $groupName, $userId);
        
        // Criador é owner
        $this->database->addConversationMember($conversationId, $userId, 'owner');
        
        // Adicionar membros
        foreach ($memberIds as $memberId) {
            $memberUser = null;
            
            // Buscar por UUID ou email/phone
            if (preg_match('/^[0-9a-fA-F-]{36}$/', $memberId)) {
                $memberUser = $this->database->getUserById($memberId);
            }
            if (!$memberUser) {
                $memberUser = $this->database->getUserByEmailOrPhone($memberId);
            }
            
            if ($memberUser) {
                $this->database->addConversationMember(
                    $conversationId, 
                    $memberUser['user_id'], 
                    'member'
                );
            }
        }
        
        $response->setSuccess(true);
        $response->setMessage("Group created successfully");
        // ...
    }
}
```

#### 4.2.4 Listagem de Mensagens com Atualização de Status (`MessageService.php`)

**Linhas 96-165**:
```php
public function ListMessages(ListMessagesRequest $request): ListMessagesResponse
{
    $response = new ListMessagesResponse();
    
    try {
        $conversationId = $request->getConversationId();
        $userId = $request->getUserId();
        
        // IMPORTANTE: Marcar mensagens como DELIVERED quando destinatário busca
        // Apenas mensagens que NÃO foram enviadas pelo próprio usuário
        $deliveredCount = $this->database->markMessagesAsDelivered($conversationId, $userId);
        
        if ($deliveredCount > 0) {
            $this->logger->info('Messages marked as delivered', [
                'conversation_id' => $conversationId,
                'recipient_user_id' => $userId,
                'count' => $deliveredCount
            ]);

            // Publicar evento no Kafka para notificar remetente
            $event = [
                'event_type' => 'messages_delivered',
                'conversation_id' => $conversationId,
                'recipient_user_id' => $userId,
                'count' => $deliveredCount,
                'timestamp' => date('Y-m-d H:i:s')
            ];
            $this->kafkaProducer->publish($event, $conversationId);
        }
        
        $messagesData = $this->database->getMessagesByConversation($conversationId, $limit, $offset);
        
        // Mapear para objetos protobuf
        $messages = [];
        foreach ($messagesData as $data) {
            $msg = new Message();
            $msg->setMessageId($data['message_id']);
            $msg->setFromUserId($data['from_user_id']);
            $msg->setFromUsername($data['from_username'] ?? '');
            $msg->setContent($data['content']);
            $msg->setStatus($data['status']);
            // ...
            $messages[] = $msg;
        }
        
        $response->setSuccess(true);
        $response->setMessages($messages);
    }
    // ...
}
```

**Conceito**: A listagem é **side-effect aware** — ao buscar mensagens, automaticamente marca como `DELIVERED` as que não foram enviadas pelo próprio usuário.

#### 4.2.5 Router Worker - Consumidor Kafka (`KafkaConsumer.php`)

**Linhas 51-90**:

```php
// Configurações de tolerância a falhas
$conf->set('enable.auto.commit', 'false');      // Commit manual
$conf->set('auto.offset.reset', 'earliest');     // Reprocessar se novo consumer
$conf->set('session.timeout.ms', '10000');       // 10s sem heartbeat = morto

$conf->set('max.poll.interval.ms', '300000');    // 5min entre polls
```

**Linhas 100-150** (loop de consumo):
```php
public function consume(bool &$shutdown): void
{
    $this->topic->consumeStart(0, RD_KAFKA_OFFSET_STORED);
    
    while (!$shutdown) {
        $message = $this->topic->consume(0, 1000);
        
        if ($message === null) continue;
        
        switch ($message->err) {
            case RD_KAFKA_RESP_ERR_NO_ERROR:
                try {
                    // Processar mensagem
                    $this->processor->process($message->payload);
                    
                    // COMMIT MANUAL: Só após sucesso
                    $this->topic->offsetStore($message->partition, $message->offset);
                } catch (\Exception $e) {
                    // NÃO commita em caso de erro
                    // Mensagem será reprocessada no próximo restart
                }
                break;
            // ...
        }
    }
}
```

**Garantias**:
- **At-least-once delivery**: Commit só após processamento
- **Idempotência necessária**: UUID como PK evita duplicatas em reprocessamento

### 5.2 Limitações Identificadas

#### Limitação 1: Kafka Consumer Single-Partition

**Problema** (`KafkaConsumer.php:109`):
```php
$this->topic->consumeStart(0, RD_KAFKA_OFFSET_STORED);
//                         ^ Apenas partição 0!
```

**Impacto**: Apenas 1/5 das mensagens são consumidas (tópico tem 5 partições).

**Solução**:
```php
// Migrar para High-Level Consumer
$consumer = new \RdKafka\KafkaConsumer($conf);
$consumer->subscribe(['messages']);
while (true) {
    $message = $consumer->consume(1000);
    // Auto-assignment de todas as partições
}
```

#### Limitação 2: Fan-out em Grupo não Otimizado

**Problema**: Para grupo de 100 membros, 1 mensagem gera 99 notificações sequenciais.

**Impacto**: Latência O(n) no número de membros.

**Solução**: Paralelizar notificações:
```php
// Usar ReactPHP para notificações paralelas
$promises = [];
foreach ($members as $member) {
    $promises[] = $this->notifyAsync($member);
}
await(all($promises));
```

#### Limitação 3: Listagem de Conversas Ineficiente

**Problema** (`ConversationService.php:145-170`):
```php
// Para cada conversa, faz query adicional para buscar nome do outro usuário
foreach ($conversationsData as $data) {
    if ($data['type'] === 'private') {
        $fullConv = $this->database->getConversationById($data['conversation_id']);
        // N+1 queries!
    }
}
```

**Impacto**: N+1 queries; lento para usuários com muitas conversas.

**Solução**: JOIN na query original:
```sql
SELECT c.*, 
       (SELECT username FROM users u 
        JOIN conversation_members cm2 ON u.user_id = cm2.user_id 
        WHERE cm2.conversation_id = c.conversation_id 
        AND cm2.user_id != :user_id 
        LIMIT 1) as other_username
FROM conversations c
JOIN conversation_members cm ON c.conversation_id = cm.conversation_id
WHERE cm.user_id = :user_id
```

### 5.3 Pontos Fortes

1. **Ordenação garantida**: Particionamento por `conversation_id`
2. **Idempotência**: UUID permite retry seguro
3. **Write-ahead**: Persistência antes de Kafka (durabilidade)
4. **Status side-effect**: Listagem atualiza status automaticamente
