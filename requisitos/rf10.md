# RF10 - Auditoria e Logs

---

## 1. Resumo do Requisito

> **RF10 - Auditoria e Logs**:
> - Gerar logs de auditoria para operações do sistema.
> - Registrar: evento, tipo de entidade, ID da entidade, usuário, detalhes e timestamp.

### Dependências com Outros Requisitos

| Requisito | Tipo de Dependência | Descrição |
|-----------|---------------------|-----------|
| **Todos RF** | Evento Upstream | Cada operação crítica gera entrada de auditoria |
| **RNF05** | Infraestrutura | PostgreSQL para persistência |
| **RNF09** | Observabilidade | Complementa métricas com trail detalhado |

### Conceito Teórico

Auditoria implementa o **Audit Trail Pattern**, criando um registro imutável de todas as operações críticas do sistema. Isso é fundamental para:

1. **Compliance**: LGPD/GDPR exigem rastreabilidade de acesso a dados pessoais
2. **Debugging**: Reconstruir sequência de eventos que levou a um bug
3. **Segurança**: Detectar acessos não autorizados ou comportamento anômalo
4. **Análise**: Entender padrões de uso do sistema

**Princípio**: *"Se não está logado, não aconteceu"* — toda operação que modifica estado deve deixar rastro.

## 3. Stack Tecnológica

| Componente | Tecnologia | Justificativa |
|------------|------------|---------------|
| **Banco de Dados** | PostgreSQL | ACID para garantia de persistência |
| **Coluna details** | JSONB | Flexibilidade para contexto variável |
| **Índices** | B-tree | Queries por entity, user e timestamp |

### Trade-off: JSONB vs Colunas Tipadas

**Alternativa A**: Colunas tipadas para cada detalhe
```sql
ip_address VARCHAR(45),
user_agent TEXT,
conversation_id UUID,
file_size BIGINT,
...
```

**Alternativa B (Adotada)**: JSONB genérico
```sql
details JSONB
```

**Justificativa**:
- Diferentes eventos têm diferentes contextos
- JSONB permite queries: `details->>'conversation_id'`
- Evita ALTER TABLE para cada novo tipo de evento
- PostgreSQL otimiza JSONB com índices GIN se necessário

## 4. Implementação

### 4.1 Schema de Auditoria (`init-db.sql`)

```sql
CREATE TABLE IF NOT EXISTS audit_logs (
    log_id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    event_type VARCHAR(50) NOT NULL,       -- 'user.created', 'message.sent'
    entity_type VARCHAR(50) NOT NULL,      -- 'user', 'message', 'file'
    entity_id UUID,                        -- ID da entidade afetada
    user_id UUID REFERENCES users(user_id),-- Quem executou (pode ser NULL para sistema)
    details JSONB,                         -- Contexto adicional
    created_at TIMESTAMP DEFAULT NOW()
);

-- Índices para queries comuns
CREATE INDEX idx_audit_logs_entity ON audit_logs(entity_type, entity_id);
CREATE INDEX idx_audit_logs_user ON audit_logs(user_id);
CREATE INDEX idx_audit_logs_created ON audit_logs(created_at DESC);
CREATE INDEX idx_audit_logs_event ON audit_logs(event_type);
```

### 4.2 Função de Inserção (`Database.php`)

```php
public function insertAuditLog(
    string $eventType,
    string $entityType,
    ?string $entityId,
    ?string $userId,
    array $details = []
): void {
    $stmt = $this->pdo->prepare('
        INSERT INTO audit_logs (event_type, entity_type, entity_id, user_id, details)
        VALUES (:event_type, :entity_type, :entity_id, :user_id, :details)
    ');
    
    $stmt->execute([
        'event_type' => $eventType,
        'entity_type' => $entityType,
        'entity_id' => $entityId,
        'user_id' => $userId,
        'details' => json_encode($details)
    ]);
    
    $this->logger->debug('Audit log created', [
        'event_type' => $eventType,
        'entity_type' => $entityType,
        'entity_id' => $entityId
    ]);
}
```

## 5. Consultas de Auditoria

### 5.1 Histórico de um Usuário

```sql
SELECT event_type, entity_type, entity_id, details, created_at
FROM audit_logs
WHERE user_id = 'user-123'
ORDER BY created_at DESC
LIMIT 100;
```

### 5.2 Histórico de uma Entidade

```sql
SELECT event_type, user_id, details, created_at
FROM audit_logs
WHERE entity_type = 'message'
AND entity_id = 'msg-456'
ORDER BY created_at ASC;
```

### 5.3 Eventos em Período

```sql
SELECT event_type, COUNT(*) as count
FROM audit_logs
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'
GROUP BY event_type
ORDER BY count DESC;
```

### 5.4 Tentativas de Login Falhas

```sql
SELECT 
    details->>'ip_address' as ip,
    details->>'attempted_username' as username,
    COUNT(*) as attempts
FROM audit_logs
WHERE event_type = 'user.login_failed'
AND created_at > NOW() - INTERVAL '1 hour'
GROUP BY details->>'ip_address', details->>'attempted_username'
HAVING COUNT(*) > 5
ORDER BY attempts DESC;
```

## 6. Análise Crítica

### 6.1 Conformidade com Requisitos

| Sub-requisito | Status | Evidência |
|---------------|--------|-----------|
| Logs de auditoria | ✅ | Tabela `audit_logs` |
| Campo evento (event_type) | ✅ | VARCHAR(50) NOT NULL |
| Campo tipo de entidade | ✅ | entity_type VARCHAR(50) |
| Campo ID da entidade | ✅ | entity_id UUID |
| Campo usuário | ✅ | user_id UUID FK |
| Campo detalhes | ✅ | details JSONB |
| Campo timestamp | ✅ | created_at TIMESTAMP |

### 6.2 Limitações Identificadas

#### Limitação 1: Auditoria Não Cobrindo Todas as Operações

**Problema**: Apenas algumas operações geram audit log:

| Operação | Auditoria? |
|----------|------------|
| `file.uploaded` | ✅ |
| `message.routed` | ✅ |
| `user.registered` | ✅ |
| `user.login` | ❌ |
| `conversation.created` | ❌ |
| `member.added` | ❌ |
| `message.status_changed` | ❌ |

**Solução proposta**: Criar wrapper ou aspect para auditoria automática:

```php
trait AuditableTrait
{
    protected function auditableAction(
        string $eventType,
        string $entityType,
        callable $action
    ): mixed {
        $startTime = microtime(true);
        
        try {
            $result = $action();
            
            $this->database->insertAuditLog(
                $eventType,
                $entityType,
                $result['entity_id'] ?? null,
                $this->getCurrentUserId(),
                [
                    'success' => true,
                    'duration_ms' => (microtime(true) - $startTime) * 1000
                ]
            );
            
            return $result;
        } catch (\Exception $e) {
            $this->database->insertAuditLog(
                $eventType . '_failed',
                $entityType,
                null,
                $this->getCurrentUserId(),
                [
                    'success' => false,
                    'error' => $e->getMessage()
                ]
            );
            throw $e;
        }
    }
}
```

#### Limitação 2: Sem Retenção/Archiving

**Problema**: Logs crescem indefinidamente.

**Impacto**: 
- Disco cheio eventualmente
- Queries ficam lentas

**Solução proposta**: Política de retenção com particionamento:

```sql
-- Particionar por mês
CREATE TABLE audit_logs_2024_01 PARTITION OF audit_logs
FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

-- Job de archiving (cron)
INSERT INTO audit_logs_archive SELECT * FROM audit_logs WHERE created_at < NOW() - INTERVAL '90 days';
DELETE FROM audit_logs WHERE created_at < NOW() - INTERVAL '90 days';
```

#### Limitação 3: Sem Imutabilidade Garantida

**Problema**: Não há proteção contra DELETE/UPDATE em audit_logs.

**Impacto**: Audit trail pode ser adulterado.

**Solução proposta**: Trigger de proteção:

```sql
CREATE OR REPLACE FUNCTION prevent_audit_modification()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'Audit logs cannot be modified or deleted';
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_immutability
BEFORE UPDATE OR DELETE ON audit_logs
FOR EACH ROW EXECUTE FUNCTION prevent_audit_modification();
```

#### Limitação 4: Auditoria Síncrona

**Problema**: `insertAuditLog()` é síncrono, adiciona latência à operação.

**Impacto**: Se banco lento, operação principal também fica lenta.

**Solução proposta**: Auditoria assíncrona via Kafka:

```php
// Em vez de INSERT direto
$this->kafkaProducer->publish('audit-events', [
    'event_type' => $eventType,
    'entity_type' => $entityType,
    'entity_id' => $entityId,
    'user_id' => $userId,
    'details' => $details,
    'timestamp' => date('c')
]);

// Consumer dedicado persiste no banco
```

### 6.3 Pontos Fortes

1. **JSONB para details**: Flexibilidade para contexto variado sem schema rígido
2. **Índices otimizados**: Queries por entity, user e timestamp são eficientes
3. **UUID como PK**: Evita hotspot em INSERT (vs serial auto-increment)
4. **Timestamp automático**: NOW() garante consistência

## 7. Segurança e Compliance

### 7.1 Considerações LGPD/GDPR

**Problema**: Logs podem conter dados pessoais.

**Exemplo**:
```json
{
    "username": "joao.silva",
    "email": "joao@email.com",  // PII!
    "ip_address": "189.40.XX.XX"  // PII!
}
```

**Mitigações**:
1. **Pseudonimização**: Hashear dados sensíveis
2. **Retenção limitada**: Apagar após período legal
3. **Acesso controlado**: Apenas admins podem consultar

### 7.2 Mascaramento de Dados Sensíveis

```php
public function maskSensitiveData(array $details): array
{
    $sensitiveFields = ['email', 'phone', 'password', 'ip_address'];
    
    foreach ($sensitiveFields as $field) {
        if (isset($details[$field])) {
            $details[$field] = $this->mask($details[$field]);
        }
    }
    
    return $details;
}

private function mask(string $value): string
{
    return substr($value, 0, 3) . '***' . substr($value, -3);
}
```

  - name: audit
    rules:
      - alert: HighLoginFailureRate

        labels:
          severity: warning
        annotations:
          summary: "Alta taxa de falhas de login"
          
      - alert: AuditLogGrowth
        expr: pg_table_size{table="audit_logs"} > 10e9
        labels:
          severity: warning

          summary: "Tabela audit_logs > 10GB"
